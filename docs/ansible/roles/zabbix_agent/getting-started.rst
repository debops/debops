Default configuration
---------------------

The role supports `multiple flavors of Zabbix Agent`__ included in Debian, one
if which needs to be specified using :envvar:`zabbix_agent__flavor` variable
(the default is ``C`` flavor). To change the installed flavor, the current
installation needs to be removed - to do that, you can execute the role with
and extra variable on the command line:

.. code-block:: console

   debops run service/zabbix_agent -e 'zabbix_agent__deploy_state=absent'

This will tell the role to remove the current installation. After that, by
changing the :envvar:`zabbix_agent__flavor` in the Ansible inventory, you can
install a different flavor of the Zabbix Agent.

.. __: https://www.zabbix.com/documentation/current/en/manual/appendix/agent_comparison


Example inventory
-----------------

To enable the Zabbix agent service on a host it needs to be included in the specific Ansible
inventory group:

TLS encryption
--------------

:envvar:`zabbix_agent__tls_mode` selects how the agent authenticates and
encrypts its connections to the Zabbix Server or Proxy:

``psk`` (default)
  Uses a pre-shared key autogenerated and stored via the DebOps
  ``secret/`` mechanism. Kept as the default for backwards compatibility
  with existing installations; does not require any external PKI. The PSK
  identity and the key file are only created in this mode.

``cert``
  Uses a host certificate managed by the :ref:`debops.pki` Ansible role.
  The certificate, private key and CA bundle paths are looked up
  automatically in the PKI realm selected by
  :envvar:`zabbix_agent__tls_pki_realm`, and the Zabbix Agent UNIX account
  is added automatically to the UNIX group that owns the realm's private
  files (:envvar:`zabbix_agent__tls_pki_group`, usually ``ssl-cert``).
  Without this group membership, ``zabbix-agent2`` fails to start with
  a permission error while trying to read its private key.

  The agent reads its certificate only at startup, therefore the role
  installs a :ref:`debops.pki` hook script which restarts the agent when
  the certificate in the PKI realm used by the agent is renewed.

``unencrypted``
  Plain-text connections, no TLS.

When using ``cert`` mode, the Zabbix Server needs to trust the CA which
issued the agent certificate, and the host object in Zabbix has to be
configured to use certificate-based encryption. If self-registration through
the API is used (see below), the role configures the host object
automatically; the expected certificate subject and issuer can be set using
:envvar:`zabbix_agent__api_tls_subject` and
:envvar:`zabbix_agent__api_tls_issuer`.

API self-registration
---------------------

Setting :envvar:`zabbix_agent__api_register` to ``True`` makes the role
register (or update) the current host as a Zabbix host object via the
JSON-RPC API, instead of relying on Zabbix's built-in "active agent
auto-registration" mechanism. The built-in mechanism cannot assign a TLS
certificate to a host it creates automatically, so it does not work well
together with :envvar:`zabbix_agent__tls_mode` set to ``cert`` - a host
created this way would end up requiring ``psk``/``unencrypted``, while the
agent is actually configured for ``cert``, and connections would fail.

Self-registration requires Zabbix Server 7.0 or newer, the
``community.zabbix`` Ansible collection, version 3.3.0 or newer (included in
the ``ansible`` package in Debian 13) and network access from the Ansible
Controller to the URL set in :envvar:`zabbix_agent__api_url`. The modules from
the collection always connect to the API from the Ansible Controller. The role
does not create the API token; create it in the Zabbix web interface
(:menuselection:`Users --> API tokens`) for a user allowed to manage hosts,
host groups and templates, and save it on the Ansible Controller in the DebOps
``secret/`` directory, by default in the ``secret/zabbix/api_token`` file (see
:envvar:`zabbix_agent__api_token_path`).

The host groups, linked templates, macros and tags applied to the registered
host are controlled by :envvar:`zabbix_agent__api_host_groups`,
:envvar:`zabbix_agent__api_link_templates`,
:envvar:`zabbix_agent__api_macros`, :envvar:`zabbix_agent__api_tags` and their
``group``/``host`` counterparts. The role adds the host to the ``Linux
servers`` host group and links the ``Linux by Zabbix agent`` template by
default, using the :envvar:`zabbix_agent__api_default_host_groups` and
:envvar:`zabbix_agent__api_default_link_templates` variables, so the inventory
variables only need to list the additional entries. Missing host groups are
created automatically; templates that do not exist in Zabbix stop the role
before anything is changed in Zabbix. Host groups, templates, interfaces,
macros and tags added to the host object outside of the role are preserved.

The list entries can use the ``state`` parameter to remove the host from
a host group, or remove a macro or a tag, also when they were defined on
a different inventory level or added outside of the role. Templates are only
linked by the role, never unlinked. See
:ref:`zabbix_agent__ref_api_lists` for details.

In Ansible check mode the role only queries the Zabbix API; host groups and
the host object are not created or modified. Zabbix does not return pre-shared
keys and values of secret macros, so the role sets them on every run without
reporting a change.


Known limitations
-----------------

Switching :envvar:`zabbix_agent__tls_mode` away from ``cert`` on a host
which previously used it does not revoke the Zabbix agent UNIX account's
membership in :envvar:`zabbix_agent__tls_pki_group` (usually ``ssl-cert``).
The role only ever *adds* the account to that group (via
``ansible.builtin.user`` with ``append: True``), and removing it safely
would require tracking whether the role itself granted that specific
membership in the first place, to avoid revoking access an administrator
granted on purpose. If the group is dedicated to this purpose, remove the
account from it manually after changing the TLS mode away from ``cert``.

Self-registration through the API is additive: removing a template, host
group, macro or tag from the Ansible inventory does not unlink or remove it
from the host object in Zabbix. Use the ``absent`` state for that, except for
templates, which need to be unlinked in the Zabbix web interface, as described
in :ref:`zabbix_agent__ref_api_lists`. Setting
:envvar:`zabbix_agent__deploy_state` to ``absent`` does not remove the host
object. Tags are compared by both name and value, therefore changing the value
of a tag in the inventory adds a new tag and keeps the old one, unless the old
pair is set to ``absent``. The host status
(:envvar:`zabbix_agent__api_status`) and the visible name
(:envvar:`zabbix_agent__api_visible_name`) are set on every run, overriding
changes made in the Zabbix web interface.
